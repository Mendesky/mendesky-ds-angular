載入與回饋 ​

這篇處理兩件事。第一，資料還在載入時，畫面要顯示什麼。第二，使用者按下建立、修改、刪除之後，要給什麼回饋。

做會讀寫後端的區塊、或接上送出按鈕之前，先讀這篇。

先判斷 ​

載入中 ​

「水合」指打開畫面時，向後端取回既有資料、填進欄位的過程。skeleton 是用形狀塊暗示內容位置的佔位畫面。

為什麼要在意：如果使用者在資料回來之前就操作欄位，空值會被寫回後端，蓋掉真正的資料。

區塊的狀況做法
打開時向 API 取預填值，而且欄位 blur 或選取時會寫回後端載入期間用 skeleton 蓋住整個區塊，不能操作。資料回來才換成真的表單
只讀 API、不寫回後端不必用 skeleton
從父層的快照還原，不打 API直接顯示，不用 skeleton
API 失敗、離線、逾時收起 skeleton，顯示空白表單。不跳 toast 或 Dialog
整頁資料載入前用 app-page-skeleton 佔位，避免版面跳動

送出之後 ​

「mutation」指會改變後端資料的操作：建立、修改、刪除。回饋策略分兩種：

  • pessimistic：等後端回應成功，才更新畫面。
  • optimistic：先更新畫面，後端失敗再還原。
操作策略畫面怎麼反應
Wizard、Dialog、多欄位表單按確認pessimistic按鈕轉為 loading。成功才關閉，並顯示成功 toast。失敗保留表單內容，顯示錯誤 toast
單一開關、下拉選單、就地編輯optimistic畫面立刻變。失敗還原成舊值，顯示錯誤 toast。成功通常不跳 toast
沒有存檔按鈕、逐欄自動存檔的介面optimistic例外：每存一欄就跳一顆成功 toast，依序堆疊
開關選到某個值後，要開 Wizard 補資料pessimistic選的當下不打 API。Wizard 確認才送出；取消就把開關還原
耗時操作，處理中要擋住整個畫面—用 app-process-modal 的 type="running"，處理中不能關閉

情境與範例 ​

載入中：skeleton ​

app-page-skeleton 是整頁載入用的佔位元件，沒有任何屬性。區塊層級的 skeleton 怎麼跟載入狀態同步，看下方規則「API 水合 Skeleton」。重點是 API 失敗時也要收起 skeleton，否則畫面會永遠卡在載入中。

送出中：按鈕 loading ​

html
<app-button
  variant="filled"
  color="primary"
  size="M"
  text="確認建立"
  [loading]="submitting()"
  (btnClick)="confirm()"
></app-button>
  • loading 為 true 時，轉圈取代 icon，底色不變，點擊無效，所以不會重複送出。
  • 要在 loading 時換文字，用 loadingText。
  • app-dialog 的確認按鈕也有 [loading]。
  • 送出中，Wizard 的 X、ESC、背景都不能關。X 鈕傳 [disabled]；ESC、背景與自訂的「取消」按鈕，處理函式在送出中直接 return。

操作結果：toast ​

按下面的按鈕，看成功、錯誤、含復原三種 toast。

ts
private readonly toast = inject(ToastService);

this.toast.show({ type: 'success', message: '已儲存' });
  • 整個 app 只在 app root 掛一次 <app-toast-container />。要顯示 toast 就呼叫 ToastService.show()。不要自建 toast 堆疊，否則兩套堆疊會互相遮蓋。
  • 停留時間由類型決定，不用自己傳：成功與載入中 3 秒；錯誤與帶 action 的 5 秒。
  • 只有帶 action 的 toast 可以點。其他 toast 不接收點擊，避免擋住底下的按鈕。
  • 訊息最多顯示兩行，超過的部分會直接被截掉，不會報錯。
  • 同一件事的「進行中 → 完成」用一顆 toast 原地轉換。不同的事各自一顆，依序堆疊。
ts
// 同一件事的兩個階段：先顯示進行中，完成後原地更新
const id = this.toast.show({ type: 'loading', message: '訪談表生成中', persist: true });
// …完成後
this.toast.update(id, { type: 'success', message: '已開始下載' });

耗時操作：擋住整個畫面 ​

html
<app-process-modal
  type="running"
  message="執行中請稍候"
  [isOpen]="isProcessing()"
  (dismissed)="onDone()"
></app-process-modal>
  • type="running"：白底小卡加轉圈，蓋住整個畫面，處理中不能關閉。
  • type="congratulation"：綠底慶祝卡，點背景會觸發 (dismissed)。

規則 ​

API 水合 Skeleton loading.api-hydration-skeleton

原則：Section 同時具備「開啟瞬間打 GET API 取得預填值」與「欄位 blur/select 觸發寫入 API」時，GET 未回 + 使用者先操作 = 寫入會把 null/空字串送回後端覆蓋真值。用 Loading Signal 驅動 skeleton 遮罩整段 section 在 race window 內不可互動，API 回來才切換到真實表單。禁止用反向 hydrated 旗標（雙重否定、可讀性差）。

什麼時候用：Section 內同時有「讀取 API 預填」與「寫入 API（blur/select/debounce 觸發）」；或任何 signal 在 API 回來前被使用者互動讀走會造成資料損失的情境。

情境說明規則
apiHydratedReadWriteSection 同時讀 API（GET 填 signals）且寫 API（blur/select 觸發 edit）
為什麼：四個同步點（init true / loadFromApi set(true) / apply set(false) / catch set(false)）缺一就會造成卡死或 race；消費者單點（@if）避免散落的 computed 洩漏中間態
  • loadingSignal = signal(true)；loadFromApi 第一行 set(true)
  • 對應 apply*Info 尾端（emitP1FullState 之後）set(false)
  • loadFromApi 的 .catch 必 set(false)，否則 API 失敗 → skeleton 永卡
  • HTML 用 @if (loadingSignal()) { <skeleton> } @else { <real form> }，不可並存
  • ngOnChanges initialState restore 分支 set(false)（snapshot 已含值、不必等 GET）
  • ngOnChanges reset 分支用 loadFromApiFiring 判斷：若本輪會觸發 loadFromApi，set(false) 交給 loadFromApi；否則主動 set(false)
apiHydratedReadOnlySection 只讀 API、沒有寫入 API（例如純展示或只 emit 給父層）
為什麼：沒有寫入 API 就不會有「被覆蓋」的資料損失；裝 skeleton 只是 UX 偏好，不是正確性需求
  • 不必裝 skeleton；沒有 race window 可遮
  • 若 UX 希望有 loading 視覺 → 再考慮 skeleton，但不屬於此 pattern 範疇
localSnapshotOnlySection 從 parent 的 initialState 快照還原，整段不打 API
為什麼：Snapshot 是 UI 草稿，不是後端真值；但 UI 可立即顯示，skeleton 沒有存在理由
  • ngOnChanges 偵測到 initialState 存在 → 直接從 snapshot set signals + Loading set(false)
  • 若 snapshot 不完整仍需 GET 補 → 走 apiHydratedReadWrite，snapshot 分支也要 set(false)（因為 UI 可立即顯示，GET 只補背景資料）
failSilentAPI 失敗 / 離線 / timeout
為什麼：永久 skeleton 是比錯誤訊息更糟的 UX；讓使用者能填表單 > 顯示錯誤
  • .catch callback 內第一件事：loadingSignal.set(false)
  • 接著 console.error 記錄失敗原因
  • UI 顯示空白表單（使用者可手動輸入、blur 會觸發重試）
  • 不彈 toast / dialog（避免打斷；parent 層若需 retry UI 再另外處理）
raceRetryReadRead API 對應 CQRS aggregate，剛 POST 建立後 read model 尚未就緒（race window < 1s），會回 503
為什麼：對齊後端「呼叫端應有 retry 策略」合約（QuotationAggregate.yml 的 retry 相關 description）；指數退避讓 projection 提前就緒時更快結束，總上限約 1.4s（＝api-retry.ts 的 200×2^(n-1) 退避三次加總）對後端 race window < 1s 規格留約 40% margin。實際值一律以 api-retry.ts 為準；寫成共用 const（RACE_RETRY）避免每個 service 重抄 delay 數字
  • Service 層 read pipe 套 retry(RACE_RETRY) — import { RACE_RETRY } from "src/app/core/utils/api-retry"
  • HttpContext 同時帶 SUPPRESS_API_ERROR_UI（抑制 retry 期間 503 dialog）+ SUPPRESS_NOT_FOUND_UI（保留 404 → null fallback 行為）
  • pipe 順序：retry(RACE_RETRY) 在前、catchError 在後（404 不 retry、其他 status 跑完 retry 才落到 catchError）
  • retry 用盡仍 503 → 拋給呼叫端 → 元件 catch 走 failSilent（console.error + skeleton 收起 + 不彈 dialog）
  • 不適用 PATCH / POST — 只適用 GET read model；寫入端的並行撞擊要用 serialize（concatMap）而非 retry

不要這樣做

  • 用反向旗標 `hydrated = signal(false)` → 雙重否定；@if (!hydrated()) 易讀性差，ngOnChanges 分支容易忘記翻轉
  • 忘記在 catch 內 set(false) → 網路一掉使用者看到永恆 skeleton，只能重整頁面
  • Loading signal 被散落消費（多處 computed / 多個 @if 分散判斷）→ 中間態洩漏，skeleton 閃爍
  • Skeleton 畫太細（1:1 對應每個欄位）→ 案件類型切換時 skeleton 欄位數不對，比真實表單還難維護
  • apply*Info set(false) 放在 emitP1FullState 之前 → 先關 skeleton 再 emit，中間一瞬間 @if 切到 @else 但 signals 還沒寫完，使用者看到空表單
  • ngOnChanges reset 分支無條件 set(false) → 覆蓋後置的 loadFromApi set(true)，skeleton 根本不會亮

無障礙

  • 鍵盤：Skeleton DOM 內無 tabindex / focusable 元素 → Tab 自動跳過該 section；API 回來 skeleton 銷毀 → 焦點管理交給父層（wizard 有自己的 focus-first-field 邏輯）
  • ARIA：Skeleton 容器可選 aria-busy="true"（若整段 section 有 labelled 區塊），但本 pattern 不強制 —— 短於 500ms 的 hydration 不值得通知螢幕閱讀器；超過 1 秒的 hydration 才考慮 aria-live="polite"；平台目前 GET API < 500ms，暫不加
  • 動態：Shimmer 動畫使用全域 .sk-shimmer（linear-gradient + 1.4s loop）；prefers-reduced-motion 由全域 .sk-shimmer 處理，pattern 層不重複定義

Mutation API 反饋策略 mutation.feedback

原則：依「操作代價」決定策略：多欄位表單 / wizard confirm → pessimistic（await 後才更新 UI）；原子互動（單一 toggle / select）→ optimistic（UI 先動，失敗 rollback）。原子互動若連動後續 wizard，視同 wizard pessimistic 流程——原子階段不 fire API。

什麼時候用：任何 component 觸發後端 mutation 時；設計 wizard confirm handler / toggle change / inline edit 的 API 呼叫時機與失敗反饋策略時。

情境說明規則
pessimisticWizardWizard / dialog / 多欄位表單的確認按鈕觸發 mutation
為什麼：多欄位收集代表使用者有明確意圖；失敗後看不到表單 = 必須重填所有欄位（代價高）。pessimistic 把「狀態一致性」拉到 API 確認後，failure path 保留表單讓重試成本趨近於 0。
  • 按下「確認建立」→ button 進入 [loading] 狀態（app-button loading prop，自動阻擋重複 click）
  • await API call（不先更新前端 state）
  • 成功 → 關 wizard / dialog；插入新資料（含 serviceItemId）；顯示 success toast（文案：「已新增」）
  • 失敗 → 保留 wizard / dialog 開啟；保留表單所有欄位值；顯示 error toast（文案：「建立失敗，請重試」）；button 退出 loading
  • 提交進行中：wizard 的 X / ESC / backdrop 全鎖（modal.dismissal.savingLocked）
  • 以 wizardSubmitting signal 驅動 [isSubmitting] → button loading；cancel guard；父元件 try/await/finally 控制
optimisticAtomic單一 toggle / select / inline edit 觸發 mutation（無後續 wizard）
為什麼：單一欄位操作密集、低風險；pessimistic 每次都卡 spinner 阻礙流暢操作。UI 立即反映給使用者「你的操作被接受了」的感知，失敗時 rollback 並 toast 提示即可補救。
  • UI 立刻反映新值（不等 API）
  • 背景 fire-and-await API
  • 失敗 → rollback UI 回舊值；顯示 error toast
  • 成功 → 通常不需 toast（除非是高重建成本操作，例：整帳 e-file toggle 值實際寫入後才算有效）
  • **例外：自動存檔介面（無存檔按鈕、逐欄 blur/選取即存後端，如 CEM、HDM）成功必發 per-field toast**——這類介面沒有「送出」動作，toast 是使用者唯一能知道「資料真的存進去了」的訊號。文案「<中文欄位名> 已儲存」。來源：使用者 2026-07-26 定案（「成功應該要有 toast，使用者才知道該資訊有被儲存」）；CEM p1-operation 另有實測回報驅動的同向規約「清空也一律發 toast，否則使用者以為清空沒生效」
  • 同上例外的兩個實作紀律：(1) toast 必貼在 API `await` 之後、同一個 `try` 內——多數 handler 的 early-return（`if (!id) return`）在 try 之外，放錯位置會對「根本沒打 API」的路徑發假回饋；(2) **一欄一顆、依序堆疊**（`ToastService.show()`），不得取代——「存了稅籍編號」與「存了國稅局所別」是兩件事。參考實作：`shared/services/save-toast.service.ts`（SaveToastService — 本專案實作，不在 DS 套件內；同事的 web 接線 PR 已明文將它保留在 app 端）
  • ⚠️ 2026-07-27 更正：本紀律 (2) 原寫「必須單一顆 toast 原地換字（update()）而非堆疊，對齊 action.confirm-destructive.reversibleToast」，是誤讀，已推翻。兩個依據都不涵蓋逐欄存檔——(a) `reversibleToast` 的「同一操作連續觸發 → 取代不堆疊」限定在**帶「復原」action 的可還原操作**，取代是為了不累積一排失效的復原鈕；(b) `ToastService.update()` 的用途是**同一件事的「進行中→完成」原地轉場**（canonical 例＝訪談表列印產 PDF：生成中→已開啟列印／已開始下載，見 ds-components-data.js id `process-toast`），那是一件事的兩個階段、不是兩件事。發現路徑：使用者實測回報「CEM 會堆疊、HDM 會直接替換」，追查後確認 HDM 實作誤引本條、且誤讀被寫回本檔
  • duration 由型別決定，呼叫端不自帶：success / loading → 3000ms、error → 5000ms、有 action → 5000ms（使用者 2026-07-27 拍板；先前 error 的 5 秒靠 22 個呼叫點手打，漏帶就退回 3 秒）。實作於 `ToastService` 的 `resolveDuration()`，`show()` 與 `update()` 共用——`update()` 會改 type（loading→error），只改一處會讓轉場後的 error 只停 3 秒
  • 文案長度：`.toast__msg` 有 `-webkit-line-clamp: 2`，過長**不報錯、直接靜默截斷**。上限 success/loading 16 全形寬、error 24、有 action 18；硬截斷點約 29（size S 桌機兩行）。插值的 runtime 長度必須有界——不定長清單（`join`）、公司名、檔名不得塞進 toast，改用「N 家／N 筆」計數，明細改 dialog 或頁面內呈現。守門：`npm run check:toast-copy`。上限數字與守門腳本皆為本專案自訂、不在 DS 套件內——DS 交付的是「兩行截斷」這個視覺約束事實，上限幾字取決於各產品的語言與語境（中英文容忍度不同）。2026-08-14 實查：Ant Design 有文案規範頁但只有定性建議、無字數上限、無工具；Bootstrap 完全不提文案；Atlassian 的 ESLint plugin 明文「並非內容或文案規範」——三個主流 DS 都不用工具管文案長度
  • 進行中可選：spinner 覆蓋原子元件（如 select）或維持 optimistic 無 spinner
pessimisticTriggersWizard原子互動（toggle / select）選到特定值後需要開 wizard 補資料
為什麼：若原子 change 同時 fire API + 開 wizard，wizard 收集到的補充欄位「後端先拿到 null 版本」→ 422；設計意圖是 wizard 確認後才算一次完整 mutation。分離兩條路徑才能保證資料完整性。
例：稅務帳 marker A 整帳需求 `no → yes`：cardChange 冒泡觸發 syncCardToBackend，configFieldChange 冒泡開 reorg wizard。修法：syncCardToBackend sig 過濾 `reorg-needed`；只有 wizard confirm 才呼叫 addAccountingReform。
  • 原子操作階段：不 fire 任何後端 API（哪怕 sig 已變更）
  • 開 wizard 收集缺少的欄位
  • Wizard confirm 才是唯一的 API fire 時機（視同 pessimisticWizard）
  • 使用者取消 wizard → 將原子元件值 rollback 到觸發前的狀態
  • 技術實作：若 HTML 同時冒泡 (cardChange) 與 (configFieldChange)，syncCardToBackend 必須過濾觸發 wizard 的 config key（使其 sig 不變、early return），由 configFieldChange handler 獨立控制流程
savingLockedSurfaceWizard / dialog 的 loading 中斷保護（與 modal.dismissal.savingLocked 對齊）
為什麼：使用者在 API in-flight 時關掉 wizard 會導致「後端建立成功但前端不知道」的 ghost state；全鎖比允許部分互動更可預測。
  • wizardSubmitting = true 時：X 按鈕、ESC、backdrop 點擊全部 no-op（見 modal.dismissal.savingLocked）
  • ng-content 的「取消」按鈕也需 guard：if (this.wizardSubmitting()) return;
  • 保護範圍：整個 try/await/finally 區間，不只是 API call 本身

不要這樣做

  • 原子 toggle 直接 fire 後端，但該 toggle 會觸發後續 wizard → 後端先拿到不完整資料（422）；正確：原子階段不 fire，wizard confirm 才是 mutation 時機（本次 reorg-needed bug 的根因）
  • Wizard confirm 不 await API 直接關 wizard → 使用者以為完成，但 API 可能失敗，前後端狀態不一致
  • Optimistic update 有 fire API 卻沒寫 rollback → API 失敗後 UI 顯示不存在的狀態，無告知
  • 成功或失敗都不給 toast → 使用者無法確認「動作有沒有成功」，需回頁面驗證
  • API 失敗時清空 wizard 表單值 → 使用者必須重填所有欄位，重試成本高
  • Pessimistic wizard 但 wizardSubmitting guard 未覆蓋 X / ESC / backdrop → API in-flight 時可關掉 wizard，產生 ghost state
  • 用文字切換 button text 代替 [loading] prop → 缺少 spinner 視覺、缺少自動 click 阻擋、語意不明確

無障礙

  • 鍵盤：按鈕 loading 中：aria-disabled="true"（仍可被 Tab 聚焦）+ aria-busy="true"；native disabled 改用 aria 方式；Success / error toast：aria-live="polite"（success）/ aria-live="assertive"（error）；不搶焦點；Wizard loading 中 ESC 不關閉（modal.dismissal.savingLocked）；失敗保留 wizard：焦點回到第一個 invalid 欄位（若能定位），或維持在確認按鈕上
  • ARIA：Loading button：aria-busy="true"；Toast：role="status"（success）/ role="alert"（error）；Wizard 全鎖中：wizard 容器加 aria-busy="true"
