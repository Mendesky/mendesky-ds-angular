確認與破壞性動作 ​

刪除、封存、撤回這類動作，要不要先問使用者？要怎麼問？這篇幫你選。另外也處理一種常被混淆的情況：動作本身不危險，但執行前要使用者先聲明某個前提成立。

設計會移除資料、或讓流程倒退的按鈕之前，先讀這篇。

先判斷 ​

先問一個問題：做錯了，要花多少功夫恢復？這叫「重建成本」。系統保留每一次變更的紀錄，所以「不可復原」真正的意思是恢復很費工，而不是資料消失。

再看有沒有「下游副作用」，也就是這個動作會不會連帶影響其他資料或流程。

情況例子做法元件
重建成本低、沒有下游副作用刪除清單項、移除欄位、取消標記直接執行，成功後跳出含「復原」的 toastapp-process-toast（透過 ToastService）
逆流程、重建成本高，常帶下游副作用封存項目、撤回已送出的申請先開警示 Dialog 打斷，寫清楚後果app-dialog，propClass="Warning"
動作風險低，但要使用者聲明某個前提成立發布前確認內容已經過審核；送出前再看一次設定在主按鈕旁放勾選聲明，不開 Dialogapp-inline-confirm

第三列不是破壞性動作。它的目的不是擋住誤操作，而是讓使用者多看一眼、正式簽名。不要把它歸到第二列。

情境與範例 ​

可還原的刪除：先做，再給「復原」 ​

  • 動作立刻執行，API 同步寫入。成功才顯示 toast。
  • 「復原」的 onClick 通常是呼叫還原 API，把已寫入的動作反轉。它不是取消一個還沒送出的請求。
  • toast 自己消失，代表使用者沒有反悔，不會觸發 onClick。
  • 停留時間由類型決定，不用自己傳。帶「復原」的 toast 停留 5 秒。
  • 只有帶 action 的 toast 可以點。
ts
private readonly toast = inject(ToastService);

this.toast.show({
  type: 'success',
  message: '已刪除「附件 A」',
  action: { label: '復原', onClick: () => this.restoreAttachment() },
});

逆流程、高重建成本：用警示 Dialog 打斷 ​

html
<app-dialog
  [isOpen]="showDialog"
  header="刪除聯絡窗口資料"
  content="此動作無法復原，請確認是否刪除該位聯絡窗口資料"
  propClass="Warning"
  confirmText="確認刪除"
  [loading]="deleting()"
  (cancel)="showDialog = false"
  (confirm)="onDelete()"
></app-dialog>
  • propClass="Warning"：確認按鈕變紅。它只代表嚴重程度，不等於「刪除」。
  • confirmIcon：預設是垃圾桶，只留給真的刪除或移除資料的動作。其他確認（取消封存、復原、送出、匯入）傳 confirmIcon=""，紅色仍保留。
  • confirmText：寫出具體動作，例如「封存此項目」，不要只寫「確認」。
  • content：寫出會發生什麼、要恢復得做哪些事，不要只問「確定嗎？」。
  • cancelText：預設「取消並關閉」，可以依情境改。
  • [loading]：API 送出中，確認按鈕顯示轉圈並停用；取消按鈕不受影響。

觸發按鈕放在選單裡時，危險項目用 variant="ghost"、color="danger"，見 app-action-menu 說明的「內容元件規範」。

前提聲明：勾選後才能繼續 ​

下面的範例要先勾選，「下一步」才能按。

html
<app-inline-confirm
  requirement="required"
  label="發布前請確認內容已經過審核"
  description="未確認前無法發布。"
  checkLabel="我已確認內容已經過審核"
  [(confirmed)]="reviewed">
</app-inline-confirm>
<app-button text="下一步" [disabled]="!reviewed()"></app-button>
  • 文案用宣告句，例如「我已確認內容已經過審核」，不用問句。
  • 元件不控制主按鈕。父層自己綁 [disabled]="!reviewed()"。
  • requirement="required"：主按鈕依賴這個勾選。requirement="optional"：複核式提醒，元件自動加上「（選填）」，主按鈕通常保持可按。
  • 離開頁面再回來，父層要把勾選狀態設回 false。元件不會自己重置。

規則 ​

破壞性動作確認策略 action.confirm-destructive

原則：系統保留每一次變更紀錄（如 Event Sourcing）時，「不可復原」的真實意涵是「重建成本」不是資料遺失。確認策略按「重建成本 + 中斷必要性 + 前提依賴性」分三層：可快速重建 → toast + undo；逆流程 / 高重建成本 → dialog 強制中斷；有前提依賴 → inline 讓使用者主動宣告前提為真

什麼時候用：設計刪除 / 封存 / 撤回 / 解散 / 跨單位協調 / 高價值設定送出等動作，需決定要用 toast、dialog 還是 inline confirm 時

情境說明規則
reversibleToast輕量可還原操作：事件可 replay、重建成本低、無下游副作用（刪除清單項、移除欄位、取消標記、解散組合等）
為什麼：過度中斷是 UX 最大浪費。事件系統天然支援 replay，undo 視窗只是把「心理保險」外顯化；有 undo 的 toast 心理成本 ≈ 0，但打斷流程的 dialog 每次都多花 2–3 秒專注力
  • 操作立即執行（不先問）且 API 同步寫入；成功才顯示 success toast，失敗顯示 error toast
  • 執行後顯示 app-process-toast，含「復原」action
  • 復原視窗預設 5 秒（可延長至 10 秒，視操作成本）
  • toast 消失 = UI 計時結束，動作早已寫入；期間按「復原」= 呼叫還原 API 反轉（非取消 pending 寫入）
  • 同一操作連續觸發 → 以最新的 toast 取代，不堆疊（避免累積一排已失效的「復原」鈕）
  • ⚠️ 本條**限帶 undo action 的可還原操作**，不涵蓋自動存檔的 per-field toast——那類一欄一顆、依序堆疊，見 mutation.feedback.optimisticAtomic 的自動存檔例外
  • 不中斷使用者主流程（不開 dialog）
destructiveBlocking逆流程 / 高重建成本操作：技術可追溯但使用者重做成本高，且常帶下游副作用（封存項目、撤回已送出的申請）
為什麼：Dialog 的用意是「打斷 + 警告後果 + 強制聚焦」。backdrop 可關 = 使用者以手滑為由略過警告；按鈕文案寫「確認」= 使用者不知在確認什麼。這兩個細節任一鬆開，dialog 就退化成 toast 的劣化版
  • 點擊觸發按鈕 → 開 app-dialog（propClass: Warning）
  • Dialog 內容必須寫出「會發生什麼 + 重建需要的步驟」，不只寫「確定嗎？」
  • backdrop 鎖死（不可點擊關閉）
  • ESC 可關閉 = 取消；唯一推進路徑是點「確認」按鈕
  • 確認按鈕文案具體化（「封存此項目」而非「確認」）
  • 高風險操作建議加 app-process-modal 顯示後續處理進度

不要這樣做

  • 刪除單一清單項也彈 dialog → 過度中斷，使用者疲勞 → 改用 toast + undo
  • 封存項目用 toast + undo → 5 秒窗口太短決定高成本重建；dialog 才夠份量
  • Dialog backdrop 可點擊關閉 → 使用者手滑略過警告，等同沒確認
  • Dialog 按鈕文案寫「確認 / 取消」→ 看不出確認什麼；應寫「封存此項目 / 保留」
  • 高重建成本操作僅用 toast（如封存項目僅顯示 toast）→ 等同沒確認，5 秒 undo 不足以承載重建成本

無障礙

  • 鍵盤：Dialog：ESC = 取消（不推進）；Enter 不自動觸發「確認」按鈕（避免誤按）；Toast：Tab 可聚焦到「復原」action；ESC 關閉 toast（等同放棄復原）
  • 焦點：Dialog 打開 → 焦點移到「取消」按鈕（預防誤按確認）；Dialog 關閉 → 焦點回到觸發按鈕；Toast 出現 → 焦點不搶，使用者若要 undo 主動 Tab 過去
  • ARIA：Dialog：role="alertdialog" aria-modal="true" aria-labelledby=title-id aria-describedby=body-id；Toast：role="status" aria-live="polite"（undo action 用 button 讓螢幕閱讀器可達）

相關元件：app-dialog app-process-toast app-button app-process-modal 

前提聲明確認 action.precondition-acknowledge

原則：動作本身風險低，但需要使用者主動宣告某個前提為真（發布前確認內容已經過審核、送出前再看一次金額與條款）。設計目標不是「阻止使用者誤操作」，而是讓使用者多看一眼並正式簽名，避免「容易忘記前提」的情境。

什麼時候用：設計任何「動作可執行，但執行前需要使用者確認某個外部前提為真」的互動——如合規聲明、資料前提確認、送出前複核等。對應元件：app-inline-confirm。

情境說明規則
preconditionAck前提依賴型確認：動作本身風險低，但需要使用者主動宣告某個前提為真（發布前確認內容已經過審核、送出前再看一次設定）
為什麼：這類情境不是「動作會出事」而是「使用者容易忘記前提」。dialog 打斷流程過重；純提醒文字容易被略過。inline-confirm 的心理作用是「我正式簽過名」，讓使用者多看一眼但不中斷節奏。元件不負責控制主按鈕，讓「簽名」與「動作」職責分開，符合展示櫃而非保險箱的 DS 元件哲學
  • 使用 app-inline-confirm 元件
  • 元件由四個區塊組成：label（前提聲明主訴）+ description / bullets（補充說明或列點）+ check（勾選控制）+ 外部 app-button（由消費者控制 disabled）
  • 前提聲明用宣告句式（「我已確認 XXX」），不用問句（「XXX 嗎？」）
  • requirement 分兩級：required（高後果，如正式發布）→ 視覺較強、消費者以 [disabled]="!confirmed()" 鎖主按鈕；optional（低後果，如送出前設定複核）→ 視覺中性、checkLabel 自動附加「（選填）」，主按鈕常 enabled
  • 不組合 dialog（重複摩擦）
  • 離開頁面再回來，confirmed 由父層清空（不保留 stale state）

不要這樣做

  • contextualInline 勾了 inline-confirm 還再彈 dialog → 雙層摩擦，使用者開始跳讀
  • contextualInline 用問句文案（「已確認？」）→ 比宣告句式弱，使用者感受不到「我正式簽過名」
  • contextualInline 跨 session 保留勾選狀態 → 使用者以為上次勾過就代表這次也驗證過
  • inline-confirm 內部自帶按鈕或控制外部 disabled → 違反展示櫃原則，消費者無法組合複雜流程
  • 此情境誤歸入 action.confirm-destructive → 前提聲明不是破壞性動作，命名會誤導設計意圖

無障礙

  • 鍵盤：Inline：Space 切換 inline-confirm 的 check；Tab 循序 check → 主按鈕
  • 焦點：Inline 勾選後 → 焦點不自動跳（讓使用者自己決定下一步；元件不侵入流程）
  • ARIA：Inline：外層 role="group" aria-labelledby 指向 label；check 關聯 aria-describedby 指向 description / bullets

相關元件：app-inline-confirm app-button
