浮層怎麼選 ​

浮層是蓋在頁面上方、暫時擋住底下操作的視窗。這篇幫你決定該用哪一種浮層，再說明關閉方式、底部按鈕、完成按鈕怎麼安排。

要做彈窗、多步驟設定、或多頁編輯視窗之前，先讀這篇。

先判斷 ​

浮層分三種原型：Dialog、Wizard、Modal。依序回答兩個問題。

  1. 目的是打斷使用者、要他明確表態嗎？ 例如破壞性動作的二次確認、強制閱讀的聲明、逾時或斷線通知。是 → Dialog。
  2. 中間步驟會不會寫入後端？ 「寫入」指呼叫會改變後端資料的 API。
    • 不會，最後按完成才一次寫入 → Wizard。
    • 會，邊編輯邊逐步存檔（連續自動儲存）→ Modal。
原型典型情境用什麼元件元件命名
Dialog單一步驟、明確的是或否：破壞性確認、強制閱讀、系統事件通知app-dialog直接用 DS 元件
Wizard聚焦設定一件事；開始主流程前的資料收集app-modal-shell，常搭配 app-stepper（非必備）*WizardComponent
Modal連續自動儲存的編輯；多頁時有導航app-modal-shell，多頁時搭配 app-stepper 的 nav 模式*ModalComponent

判斷時注意：

  • 最可靠的判準是「什麼時候寫入後端」。導航能不能自由跳頁，不是判準。
  • 視窗大小、有沒有「確定／取消」兩顆按鈕，也不是判準。Wizard 的最後一步同樣有確認按鈕。
  • Dialog 不是表單容器。要收多個欄位，改用 Wizard 或 Modal。
  • app-dialog 是固定格式的小型確認框。要自訂標題、內容、底部按鈕時，用 app-modal-shell 自己組。

情境與範例 ​

關閉方式：看會不會遺失資料 ​

Modal 能不能點背景、按 ESC、按 X 關閉，取決於「關掉會不會遺失資料」。完整的分流在下方規則「Modal 關閉行為」。

元件這樣接：

  • 背景：app-modal-shell 的 canDismiss。有未儲存的變動時傳 [canDismiss]="!isDirty()"，點背景就完全沒反應。
  • ESC：不受 canDismiss 影響。shell 只發出 (escapePress)，由你決定直接關，還是先跳二次確認。
  • X：用 app-modal-close-btn 放進 header。點擊發出 (closeClick)，同樣由你決定。儲存中傳 [disabled]="saving()"。

下面的範例背景不可關閉。點背景試試看，視窗不會關。

html
<app-modal-shell
  [isOpen]="isOpen"
  [canDismiss]="!isDirty()"
  ariaLabelledBy="edit-modal-title"
  (backdropClick)="close()"
  (escapePress)="requestClose()"
>
  <!-- header：標題 + 關閉鈕 -->
  <app-modal-close-btn [disabled]="saving()" (closeClick)="requestClose()"></app-modal-close-btn>
  <!-- body、footer -->
</app-modal-shell>

大型、多步驟的 Wizard 有未儲存的內容時，按 X 或 ESC 要先跳二次確認，讓使用者選保留或捨棄。小型、單一用途的 Modal 則直接關，因為背景已經鎖住，不怕誤觸。下面是 Wizard 放棄設定時的確認框。

確認框的次要按鈕預設寫「取消並關閉」。用 cancelText 可以依情境改，例如取消新建的確認改成「繼續新建」。

底部按鈕：讓使用者知道為什麼不能送出 ​

Footer 左邊放退出流程的按鈕（取消、上一步），右邊放推進流程的主按鈕（確認、送出、下一步）。

條件不足時，主按鈕維持停用的外觀，但仍然可以點。點了之後用 tooltip 說明原因，並捲到第一個錯誤欄位。不要在 footer 放常駐的警示文字。

用 app-button 的三個屬性就能做到：

html
<app-button
  variant="filled"
  color="primary"
  size="M"
  text="送出"
  [disabled]="!canSubmit()"
  [clickableWhenDisabled]="true"
  [disabledMessage]="submitBlockers()"
  (disabledClick)="scrollToFirstError()"
  (btnClick)="submit()"
></app-button>
  • clickableWhenDisabled：改用 aria-disabled，點擊可以穿透停用狀態。
  • disabledMessage：點擊後顯示在按鈕上方的 tooltip。一條原因傳字串，多條傳字串陣列，會以條列呈現。
  • (disabledClick)：停用狀態下被點擊時觸發。在這裡捲到第一個錯誤欄位。

Footer 裡的按鈕用同一個 size。退出用 elevated，推進用 filled，對照 app-button 說明裡的「語意選用指引」。

多頁 Modal：完成按鈕放哪裡 ​

多頁 Modal 的左側導航用 app-stepper 的 nav 模式。完成按鈕（例如送出、發布）放哪裡，要看「實體」怎麼排進頁面。實體指一份資料裡重複出現的單位，例如一份申請裡的每一位成員。

  • 沒有實體，或實體已排進同一條頁序：完成按鈕放在最後一頁的底部。
  • 每個實體重複整套頁面，用切換器切換：完成按鈕常駐在左側欄底部。按下去沒通過時，未完成的頁面標紅框、實體標「缺 N 項」，並自動帶到第一個錯誤。

stepper 的 validationTriggeredIds 列出的項目會顯示紅色警告狀態。下面的範例裡，「基本資料」底下有兩個項目已觸發驗證，另有已完成與鎖定的頁面。

規則 ​

彈窗三原型：Dialog / Wizard / Modal interaction.overlay-archetypes

原則：所有覆蓋層分三種原型，用一組軸區分；這是串接 modal.dismissal / mutation.feedback / wizard.keyboard / modal.nonlinear-completion 的主幹。 ── Dialog：目的是打斷使用者（高風險/需專注）、要求明確表態（典型不給 backdrop 出口）。 ── Wizard：modal 的變體、聚焦設定一件事、常搭 stepper（非必備）；關鍵特徵＝中間不 fire write model API、完成 action 才一次 fire（放棄成本低，傾向可關）。 ── Modal：最通用、連續自動儲存（編輯即逐步寫後端/草稿）、多頁時有導航（sidebar/stepper）。 【wizard vs modal 硬判準】中間有沒有 fire write model API：有（逐步寫）→ modal；沒有、完成才寫 → wizard。導航是否自由跳轉不是判準。例如多頁 modal 開啟前的「前導設定頁」是 wizard；進入後逐步儲存的本體是 modal。 【dismissal 權威】backdrop/ESC/X 何時可關、何時二次確認，一律以 modal.dismissal 為準（依 dirty/風險：editingClean 可關、editingDirty 二次確認、readOnlyBlocking 不可關、savingLocked 全鎖）；本原型矩陣只標各原型的「典型傾向」，不是絕對規則。

什麼時候用：命名或設計任何覆蓋層元件時；判斷某互動屬 dialog / wizard / modal 哪一種；code review 發現命名與行為不符時。

情境說明規則
useDialogDialog：打斷 + 強制表態（app-dialog DS 元件）
為什麼：核心是「中斷」與「確認」：使用者主要動作被暫停，必須先表態。干擾性最高，用於高風險或需專注的場合。
  • 典型傾向：不給 backdrop 出口、必須 confirm/dismiss/完成 required action 才關（精確規則依 modal.dismissal.readOnlyBlocking）
  • 破壞性動作二次確認（刪除/封存/撤回）、強制閱讀（法律聲明）、系統事件通知（逾時/斷線）
  • 單步驟、明確 Y/N，流程本身不需多步
  • 對應 DS 元件：app-dialog（Warning / Confirm / Info variant）
  • 行為細節 → modal.dismissal.readOnlyBlocking；破壞性確認 → action.confirm-destructive
useWizardWizard：聚焦引導設定，完成才寫 API（modal 變體）
為什麼：核心是「聚焦一件事直到關閉」+「資料暫存於前端、完成才落地」。失敗保留表單、重試成本低（見 mutation.feedback）。
  • 典型傾向：放棄成本低（中間未寫任何 write API），常可 backdrop 關＝放棄；但已填較多資料時仍依 modal.dismissal（editingDirty 二次確認、savingLocked 提交中全鎖）
  • 常搭 stepper（非必備）；引導使用者設定/收集資料，中間值可跳回修改但不 fire write API
  • 只有最後完成 action 才 fire write model API（一次性提交）
  • 例子：新增資料精靈、開啟多頁 modal 前的前導設定頁、範本編輯精靈
  • 對應命名：*WizardComponent；提交策略 → mutation.feedback.pessimisticWizard；鍵盤 → wizard.keyboard
useModalModal：最通用，連續自動儲存的多頁編輯（app-modal-shell）
為什麼：最廣的原型，可單純可複雜。連續自動儲存是通則；完成 CTA 的位置由「實體維度如何長進頁面結構」決定，而非維度數量。
  • 連續自動儲存：編輯即逐步寫後端 / 自動存草稿（與 wizard 最大差別）
  • backdrop/ESC/X 關閉行為一律依 modal.dismissal：editingClean 可關、editingDirty 跳二次確認 bar、savingLocked 全鎖（不是「一律二次確認」）
  • 多頁 → 有導航（sidebar 自由跳轉 / stepper）；每頁底部可有「下一頁」CTA
  • 明確完成 CTA（送出/發布）放置依「實體維度結構」：
  • · 無實體維度 或 實體摺進頁序（by-實體頁 + 共用頁，一條頁序）→ 完成 CTA 在最後一頁底。例：每位成員各一頁＋共用頁排成一條頁序，送出鈕在最後一頁的預覽底部
  • · 實體為正交切換器（每實體重複整套頁）→ 完成 CTA 在左側欄底。例：每位成員各有整套頁、用切換器切換（見 modal.nonlinear-completion）
  • 簡單 modal（純展示/無完成閘門）→ close = 完成，無 completion CTA
  • 對應命名：*ModalComponent
howToTell三者最快判別法
為什麼：單看「有沒有 CTA」「有沒有 stepper」「modal 多大」都會誤判；用 dismissal + API 時機 + 目的三軸交叉判斷。
  • 目的傾向：強制表態不給出口 → dialog；低風險可放棄 → wizard；連續編輯 → modal（精確 dismissal 一律見 modal.dismissal，不靠這條當絕對規則）
  • 中間有沒有 fire write model API？沒有、完成才寫 → wizard；逐步寫（自動儲存）→ modal（最可靠的判準）
  • 目的是打斷確認還是設定資料？打斷/高風險 → dialog；專注設定 → wizard/modal
  • 前導頁（開主流程前的資料收集）→ wizard；主流程本體（多頁編輯）→ modal
ambiguousCase容易誤判的邊界情況
為什麼：常見錯誤是把「有 CTA 的多頁 modal」都叫 wizard、或把「有確認按鈕的」都叫 dialog；應以三軸語意判斷。
  • 「只有一步的資料收集」→ 看目的：引導完成任務 → wizard；確認已知動作 → dialog
  • 「有 OK / Cancel 兩顆按鈕」→ 不能以此判斷；wizard 最後一步也有確認按鈕
  • 「多頁 + 可自由切換」→ 仍要看 API 時機：連續自動儲存 → modal；完成才寫 → wizard
  • 「系統自動觸發」→ 系統事件通知用 dialog；引導設定流程即使自動觸發也是 wizard

不要這樣做

  • 把多步驟資料收集命名為 *DialogComponent → 應為 *WizardComponent
  • 把破壞性動作確認命名為 *WizardComponent → 應為 app-dialog + action.confirm-destructive
  • 用 app-dialog 承載多欄位表單 → dialog 不是表單容器，改用 wizard 或 modal-shell
  • 把「連續自動儲存的多頁編輯本體」叫 *WizardComponent → 它逐步寫 API，是 modal，應為 *ModalComponent
  • 把「中間不寫、完成才一次寫」的前導收集叫 modal → 它是 wizard
  • 以導航是否自由跳轉判斷 wizard/modal → 判準是 write API 時機，不是導航自由度
  • 以 modal 大小或「有沒有 CTA」判斷原型 → 應以 dismissal + API 時機 + 目的三軸判斷

無障礙

Dialog：焦點 trap，關閉後焦點回觸發按鈕；ESC 行為見 modal.dismissal.readOnlyBlocking。Wizard：Tab trap；每步驟切換焦點移至步驟標題/第一欄位；提交中全鎖（mutation.feedback）。Modal：Tab trap；多頁切換焦點移至頁標題；dirty 關閉二次確認。三者皆 aria-modal="true" + aria-labelledby。

相關元件：app-dialog app-modal-shell app-button app-stepper 

Modal 關閉行為 modal.dismissal

原則：有資料損失風險 → 強制確認出口（X + 二次確認，鎖 backdrop）；無風險 → 最低退出成本（backdrop 即可關）；儲存中 → 全鎖，避免 race condition

什麼時候用：設計或擴充 modal / dialog 類 dismissable surface 時；討論 X 按鈕 / ESC / backdrop 三出口策略時（drawer 的關閉行為見 drawer-shell 元件說明）

情境說明規則
readOnlyDismissible唯讀檢視 modal（展示資訊、無互動成本）
為什麼：誤關代價 = 再開一次（2 秒），應降低退出成本
  • 大面積 backdrop 可點擊關閉
  • ESC 可關閉
  • X 按鈕可選（不強制；有 X 較明顯但也增加視覺噪音）
readOnlyBlocking唯讀但強制閱讀（如條款同意前的聲明 modal）
為什麼：關閉代價 = 法律 / 合規風險；必須強制閱讀互動
  • 必須顯示明確的「我已閱讀」或「確認」按鈕作為唯一出口
  • backdrop 不可關閉
  • ESC 不可關閉（防止習慣性按 ESC 跳過閱讀）
  • X 按鈕不出現
editingDirty編輯型且含未儲存變動（dirty=true）
為什麼：誤觸 backdrop 代價 = 整份表單資料遺失 → 一律鎖 backdrop。但 X / ESC 是明確意圖：大 wizard 填寫成本高，二次確認把成本從「重填」降到「多一次 click」；小 modal 成本低，二次確認反而過度打擾（見 antiPattern「空白表單也被打擾」之對偶），故僅大 wizard 二次確認
  • 右上角 X 按鈕必須顯示（明確出口）— 用共用 app-modal-close-btn（No-X-Cancel + propClass="Modal"）
  • backdrop 不可直接關閉（app-modal-shell [canDismiss]="!isDirty()" 擋；ESC 不受此 gate）
  • X / ESC 行為依填寫成本分層：大型 / 多步驟 wizard（如多頁設定精靈、新增資料精靈）→ 二次確認（保留 / 捨棄）；小型單一用途 modal（如重新命名、封存、合併、拆分）→ X / ESC 直接關（backdrop 鎖已足夠防誤觸）
editingClean編輯型但內容未變動（dirty=false，含表單有驗證錯誤但尚未 dirty）
為什麼：沒有資料可失 → 不該強加額外摩擦
  • backdrop 可關閉（視同 readOnlyDismissible）
  • ESC 可關閉
  • 無二次確認
savingLocked儲存中 / 非同步操作進行中
為什麼：關閉中途 = 資料狀態未知（race condition）；避免使用者以為已儲存但其實失敗
  • X / ESC / backdrop 全鎖
  • 按鈕顯示 loading 狀態
  • 必要時顯示「正在儲存…」提示

不要這樣做

  • 唯讀 modal 同時放 X 與允許 backdrop 關閉 → 兩個出口、視覺噪音
  • 編輯 modal 不管 dirty 狀態一律二次確認 → 空白表單也被打擾
  • 小型單一用途 modal（重新命名、封存等）也強制二次確認 → 過度打擾（X/ESC 直接關即可，backdrop 鎖已防誤觸）
  • backdrop 關閉前沒檢查 dirty → 資料靜默遺失
  • 儲存中仍允許 ESC 關閉 → 儲存結果不明、資料狀態 race
  • 強制閱讀聲明 modal 給 backdrop 關閉 → 使用者繞過合規互動
  • nested modal 開啟時，下層 disabled-tooltip portal 未關閉 → tooltip 穿透到上層 modal（修法：tooltip portal 監聽 ModalStackService.stackSize，開啟時 snapshot 深度，stack 增層時主動 close portal）

無障礙

  • 鍵盤：ESC closes when type !== readOnlyBlocking && type !== savingLocked；Tab trap inside modal（焦點不逸散到底層頁面）；Shift+Tab 同樣 trap
  • 焦點：Open → 焦點移至第一個 focusable 元素（X 按鈕或首個輸入欄位）；Close → 焦點回到觸發 modal 的按鈕
  • ARIA：role="dialog"；aria-modal="true"；aria-labelledby 指向 modal 標題 id；savingLocked 時加 aria-busy="true"

相關元件：app-modal-shell app-modal-close-btn app-dialog 

Modal Footer Button 位置與錯誤回饋 modal.footer-buttons

原則：明確提交型 modal 的 footer：左側放退出流程的被動動作（取消／返回／上一步），右側放推進流程的主動作（確認／送出／下一步）；主動作在條件不足時保持 disabled 外觀但允許點擊，點擊後以 tooltip 就地顯示原因，不以常駐警示文字佔用 footer 版面

什麼時候用：設計或審查 dialog、wizard、modal 的 footer button（含明確完成/送出 CTA）排版與送出前驗證機制時。連續自動儲存型 modal 無 per-field save/cancel，但其最後一頁的完成 CTA（如「送出」）仍適用本 pattern——見 continuousSaveException scenario 與 interaction.overlay-archetypes。

情境說明規則
footerLayoutFooter 左右分區原則
為什麼：對齊 Material / Atlassian / Apple HIG：右側是視覺重心與拇指熱區，放主動作降低操作成本；左側被動動作符合「往左＝退出」的空間語意；flex container 規則來自實測：wizard 的上一步（有 icon）與取消（無 icon）以 inline-flex 排列時文字基線錯位，加 flex 包裹後消除
  • 左側：取消、關閉、返回、上一步（退出或回退流程）
  • 右側：確認、送出、下一步、發布（推進流程的主動作）
  • 多步驟 wizard：上一步在左，下一步在右；取消在左與上一步並列
  • 單一主動作 dialog（如刪除確認）：左側取消，右側破壞性動作
  • 左側群組與右側群組必須以 display:flex + align-items:center 包裹，不可讓 app-button 以 inline-flex 散排 — inline-flex 的 baseline 由各按鈕第一個 inline-level 子元素決定（有 icon 的與無 icon 的 baseline 不同），必然錯位
disabledWithFeedback主動作條件不足時的 disabled 狀態與回饋
為什麼：使用者點了主動作才需要知道為什麼不能送：點擊觸發的就地回饋成本最低，不必用常駐的引導提示佔版面；觸控裝置可 tap，不依賴 hover
  • 主動作按鈕使用 app-button [clickableWhenDisabled]="true" [disabledMessage]="..." (disabledClick)="..."
  • 外觀仍顯示 disabled（灰底灰字），但 click / tap 可穿透
  • 點擊後觸發兩層回饋：全域錯誤顯示在按鈕正上方 tooltip；欄位級錯誤預設顯示在該欄位下方（欄位元件 errorPosition 預設 bottom；版面放不下時才改 top，2026-10-14 定案）+ scroll 到第一個欄位錯誤
  • 多個錯誤同時存在：全部 tooltip 同時顯示，scroll 到第一個欄位級錯誤
  • tooltip 持續顯示直到對應條件滿足才消失，不自動 dismiss
noFooterWarningText不在 footer 放常駐警示文字
為什麼：常駐文字讓 footer 高度不穩定；tooltip 佔用零版面、語意更精確（「你點了才需要知道為什麼不能送」）
  • footer 版面只放 button，不放說明文字或 inline 警示
  • 錯誤訊息改為 tooltip，點擊觸發、就地顯示
continuousSaveException連續自動儲存型 modal — 部分適用
為什麼：連續自動儲存 ≠ 無完成點：這類 modal 仍可能有明確的完成閘門（例如最後一頁預覽底部的「送出」），該完成 CTA 與一般送出 CTA 一樣套 footer-buttons；只是「無 per-field save / 無 cancel」（資料已逐步寫入，強套取消會讓人以為能「不儲存離開」）。
  • 典型情境：多頁編輯 modal，欄位 blur 即逐步寫後端
  • 無 per-field save 按鈕、無「取消」按鈕——資料已逐步寫入，「取消」語意模糊
  • 但最後一頁仍有明確完成 CTA（如「送出」）：該 CTA 套右側主動作 + disabledWithFeedback（disabled 外觀可點 + tooltip + scroll），本 pattern 適用於它
  • 每頁「下一頁」為純導航 CTA（不擋驗證）；驗證在各頁即時 + 最後一頁完成 CTA
  • 原型歸屬：modal（連續自動儲存），見 interaction.overlay-archetypes
unifiedSizeAndVariantFooter 按鈕統一 size，群組內 variant 一致
為什麼：app-button size 直接控制 height（btn--m=36px、btn--l=40px）—混用 size 必然文字基線錯位；同 size 但群組內混用 variant、或左右群組視覺重心差異過大，相鄰 hover 切換時會出現視覺跳動，使用者會抱怨「看起來高度不齊」即使 CSS height 完全相同
  • Footer 內所有 app-button 使用相同的 size prop（推薦全部 size="M"）
  • 左側退出群組（取消／返回／上一步）內所有按鈕使用同一個 variant
  • 左右兩群組之間的 variant 應在 default 狀態下視覺重心對等；避免一邊 default 透明、一邊 default 重色背景
  • 推薦組合：左群組 elevated（白底+陰影 hover）+ 右側 filled；或左群組 outlined（default 即帶邊框）+ 右側 filled
  • elevated variant 的 hover 才出現 box-shadow，相鄰按鈕只 hover 其中一顆時會視覺跳動 — 若體感過於明顯，改用 outlined 讓 default 即帶邊框
adjacentSameSideDivider同側相鄰按鈕之間加 vertical divider 避免誤觸
為什麼：使用者實測回饋：同側緊鄰兩顆按鈕（如上一步、取消）沒有視覺分隔時容易誤觸，特別是在觸控裝置；1px vertical divider 明確傳達「這是兩個獨立操作」，降低誤觸率，同時不佔 footer 高度
  • 同一側群組有 ≥ 2 顆 button 時，相鄰 button 之間插入 <app-divider display="Column" propClass="Grey20">
  • divider 由 flex 容器的 gap 自然隔開兩側（gap: 8px），不需手動設定 divider margin
  • 右側群組若有 ≥ 2 顆 button（如「另存草稿」+ 「送出」），同樣適用本規則
  • disabled 狀態的相鄰 button 之間 divider 仍需保留，不因 disabled 移除

不要這樣做

  • footer 右側同時放取消 + 確認 → 取消應移至左側
  • disabled 按鈕不可點擊、沒有任何錯誤回饋 → 使用者不知道為什麼不能送出
  • footer 放常駐警示文字（如「請至少選取一個項目」）→ 改用點擊觸發 tooltip
  • 連續儲存型 modal 強加取消按鈕 → 語意混淆，使用者誤以為可以「不儲存離開」
  • hover tooltip 作為唯一錯誤回饋 → 觸控裝置看不到
  • footer 內 app-button 用不同 size（如左 size="S" 右 size="M"）→ 文字基線錯位
  • 左群組混用 variant（如上一步用 ghost、取消用 elevated）→ 視覺重心不一致；hover 其一時視覺差異更明顯
  • 左/右群組的 button container 沒有 display:flex + align-items:center → 有 leftIcon 的按鈕與沒 icon 的按鈕 inline-flex baseline 不同，default 狀態就對不齊
  • 同側相鄰兩顆 button 直接緊貼、無 divider 分隔 → 誤觸率高，觸控裝置尤甚

無障礙

  • 鍵盤：disabled 按鈕使用 aria-disabled="true" 而非原生 disabled，讓鍵盤仍可 Tab 到按鈕並觸發 Enter 回饋；tooltip 出現時不搶 focus，使用者可繼續 Tab 至錯誤欄位修正
  • 觸控：tap on clickableWhenDisabled 按鈕同樣觸發 disabledClick 與 tooltip
  • ARIA：aria-disabled="true" 告知輔助技術按鈕目前無法完成主動作；tooltip 文字應以 role="tooltip" 標記，id 與 aria-describedby 對應

相關元件：app-button app-dialog 

Modal 正交多實體的 sidebar 完成驗證 modal.nonlinear-completion

原則：本 pattern 是 interaction.overlay-archetypes「modal」原型下，**實體維度為「正交切換器」（每個實體重複整套頁，如：成員切換器 × 每位成員 4 頁）** 的完成規則。因為沒有「單一最後一頁」，完成 CTA 放 sidebar 底部常駐、與當前頁/實體脫鉤；跨頁/跨實體錯誤無法在當前 DOM 直接 scroll，改用「導航樹紅框 + 實體切換器徽章」兩層錯誤地圖呈現，點 CTA 自動鑽取到第一個未完成實體的第一個未完成頁再 scroll。對照：實體「摺進頁序」（by-實體頁 + 共用頁，一條頁序，完成鈕在最後一頁）→ 完成 CTA 在最後一頁底，**不套本 pattern**。disabled+tooltip+scroll 基礎機制沿用 modal.footer-buttons.disabledWithFeedback。

什麼時候用：設計「實體正交切換器」結構的多頁 modal（每實體重複整套頁）的完成送出點與跨頁/跨實體驗證錯誤呈現時，如一份申請含 N 位成員、每位成員 4 頁。不適用於：摺進頁序型 modal（完成在最後一頁）、wizard（完成才 fire API）、Y/N dialog。

情境說明規則
sidebarCompletionCta完成 CTA 放 sidebar 底部，與當前頁脫鉤
為什麼：非循序表單沒有「最後一頁」的概念，完成動作是跨所有頁/實體的單一閘門；放 sidebar 底部讓它與當前位置脫鉤、隨時可送。單一總結 tooltip 對齊 footer-buttons「不放常駐警示文字」原則。
  • 單一完成動作（如「完成建立資料」）放左側 sidebar 導航最底部，常駐顯示
  • 不綁在任一頁的內容區 footer——頁面可自由切換，送出點不該隨「當前在第幾頁」變動
  • disabled 外觀但可點（app-button [clickableWhenDisabled]="true" + [disabledMessage] + (disabledClick)），沿用 modal.footer-buttons.disabledWithFeedback 的就地回饋機制
  • CTA 身上只掛「一個」總結 tooltip（如「尚有 N 位成員未完成」/「尚有 N 個頁面待完成」），不在每個導航項各掛 tooltip
twoLevelErrorMap跨頁/跨實體錯誤用兩層導航地圖呈現，而非單一錯誤清單
為什麼：tooltip 一次只能優雅顯示一個，多個導航項各掛 tooltip 會重疊且為暫態，不適合當常駐錯誤地圖；導航樹紅框 + 實體徽章本就是常駐可掃視的結構。對標 GOV.UK error summary「每條錯誤可定位」精神，但用既有導航樹取代獨立 summary 元件，省版面又貼合非循序結構。
  • 頁層級：導航樹（app-stepper）未完成頁的 pill 顯示紅框 warning 狀態
  • 實體層級（多位成員）：實體切換器（成員面板）每個實體顯示完成綠勾 / 「缺 N 項」徽章（app-label，純文字不加 icon）
  • 點完成 CTA 時把所有未完成頁/實體一次點亮（常駐、可掃視），不靠暫態 tooltip 列舉
  • 徽章用文字 + 顏色雙重編碼（不只用顏色），色盲友善
autoDrillToFirstIncomplete點未通過 CTA 自動鑽取到第一個錯誤
為什麼：延伸 modal.footer-buttons 的「scroll 到第一個錯誤」動線到二維（實體 × 頁）；給使用者明確下一步，不必在多個紅點間自己摸索。
  • 點 disabled 完成 CTA → 觸發驗證（唯一入口）
  • 鑽取順序：第一個未完成實體 → 切到該實體 → 其第一個未完成頁 → 切到該頁 → smooth scroll 到第一個錯誤欄位
  • 跨實體/跨頁切換後需等 DOM render（雙 requestAnimationFrame）再 query 錯誤欄位 scroll，避免抓到舊實體/舊頁 DOM
  • 使用者亦可自行點任何紅框 pill / 紅點徽章直接導航過去（兩層地圖皆可點）
reuseDisabledFeedback就地回饋機制沿用 footer-buttons，不重造
為什麼：避免知識重複：disabled-but-clickable + tooltip + scroll 的基礎機制在 footer-buttons 已定義；本 pattern 與它是同域（modal）的版面變體（footer vs sidebar），引用而非複製。
  • disabled 外觀 + 可點 + 點擊後 tooltip 就地顯示原因 + scroll 到錯誤——直接沿用 modal.footer-buttons.disabledWithFeedback
  • 本 pattern 只擴充「跨頁/跨實體」部分（兩層地圖 + 鑽取），不重新定義 disabled feedback 的基礎行為
  • tooltip 持續顯示直到對應條件滿足才消失（同 footer-buttons）

不要這樣做

  • 把多個 tooltip 同時掛在各導航項上 → 重疊、暫態，不適合常駐錯誤地圖；改用導航樹紅框 + 實體徽章
  • 完成 CTA 綁在某一頁的內容區 footer → 非循序表單會讓使用者以為「只驗這一頁」
  • 多成員錯誤只用單層導航紅框（pill）→ 只反映當前實體，看不到其他未完成實體；需補實體切換器徽章
  • 把「摺進頁序」結構（by-實體頁＋共用頁）硬套 sidebar 完成 CTA → 它有單一最後一頁，完成應在最後一頁底，不套本 pattern
  • 把連續自動儲存的多頁 modal 命名/設計成 wizard → 它逐步寫 API，是 modal，見 interaction.overlay-archetypes
  • 徽章只用顏色（紅點）不加文字 → 色盲不友善；用 app-label 文字「缺 N 項」

無障礙

disabled CTA 用 aria-disabled="true"（非原生 disabled），鍵盤仍可 Tab/Enter 觸發回饋；tooltip 出現不搶焦點；自動鑽取切換實體/頁後焦點與 scroll 目標移至第一個錯誤欄位；導航徽章文字 + 顏色雙重編碼。
